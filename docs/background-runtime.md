# Background Agent execution

The current source uses the [dual-document architecture described below](#dual-document-execution-architecture-after-the-429-build). Earlier ownership descriptions and pinned emulator results are retained as historical context for their original single-document APKs.

`AgentRuntimeService` owns one `AgentRuntimeEngine`, which owns the WebView execution document, TrustedWebViewBridge, ProductHost/SQLite writer and in-memory Pi sessions. MainActivity binds to the service and attaches the same WebView. Leaving the foreground, destroying the Activity or returning to chat does not close a running engine. The WebView uses MutableContextWrapper and returns to application context when detached; Activity-only UI callbacks are weak references. Microphone capture remains Activity-owned and stops when the screen pauses.

Every normal user send acquires a bounded service work hold before model-profile checking; Native `begin` admission also verifies foreground execution. The hold spans a custom configuration probe and the actual Run, preventing an Android foreground-start eligibility gap when the user leaves during the probe. A work hold grants no network/device authority and is released in the outer send cleanup, including cancellation. The foreground notification identifies ongoing work and provides a Stop all tasks action. This stops all Pi executions and immediately revokes Native device authority, while normal durable terminal processing preserves the partial conversation. The fixed `agent.background` tool can move only this app’s attached chat task behind other apps, through the normal Native checkpoint; it accepts no arbitrary task, package, URI or shell command. A detached/already hidden chat reports that state without submitting a task change. A successful Android request still requires subsequent screen observation to establish what is visible. Multiple runs share one engine/writer. No new Activity, including display moves and recreation, creates a second writer.

The manifest declares `FOREGROUND_SERVICE` and, for Android 14+, `FOREGROUND_SERVICE_SPECIAL_USE` plus the required `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` explanation. Special use represents user-started interactive on-device Agent control, which does not fit a timed data transfer or short service. The implementation does not use `dataSync` or `shortService` and introduces no task/service wall-clock deadline. Android 13+ notification permission is requested only from the explicit settings action, never as a gate to starting a task. Android allows the foreground service even if this permission is denied, but its notice is then in the system active-apps surface rather than the notification drawer. Service startup still obeys Android foreground-start eligibility; failure to establish foreground execution rejects Native begin before effects.

When all runs finish, foreground status is removed. If no Activity is bound, the idle service closes its engine. The service returns START_NOT_STICKY: OS termination, explicit OS stop, or renderer death does not restart/replay a task. Durable history is recovered as interrupted on the next explicit opening. This is not a promise of survival after force stop or process/renderer death.

Settings save explicitly reloads an idle engine because its Native model/network profile is immutable. Activity recreation by itself only reattaches. Reload refuses while any Native run remains active, awaits the old writer’s closeCompletion before creating its replacement, and preserves conversations/skills/credentials.

- [Foreground service types and specialUse](https://developer.android.com/develop/background-work/services/fgs/service-types)
- [Launch a foreground service and startup restrictions](https://developer.android.com/develop/background-work/services/fgs/launch)
- [Notification runtime permission and foreground services](https://developer.android.com/develop/ui/views/notifications/notification-permission)

`EmulatorBackgroundRuntimeTest` uses a loopback real Responses SSE provider and an actual configuration probe, with a disposable Native-only fixture key. It checks HOME + Activity finish, same host/WebView on return, same Pi session on follow-up, real foreground notification action cancellation, durable partial context and no replay. It requires an emulator with no saved model key and POST_NOTIFICATIONS granted for notification-action inspection. It also holds an idle writer’s close for longer than the old semaphore wait and verifies reload stays asynchronous and creates no second owner before close completion. It never operates Thor or sends device input.

## Dual-document execution: architecture after the 429 build

The current source separates the service-owned execution document from the chat display. The earlier APK results above describe their original single-document implementation; their passes are not transferred to this architecture.

The service creates `executionWeb` with application context, calls `onResume()` before loading `runtime.html`, and never attaches that WebView to an Activity or window. It alone owns the Runtime, Native bridge, ProductHost/SQLite writer and Pi sessions. A separate chat WebView loads `index.html` with a restricted display proxy. Activity attach/detach, UI settings, microphone and picker callbacks use this chat document. There is no overlay, artificial window visibility, audio keepalive, or scheduler-related change to the actual device target windows, focus, screenshots or input authorization.

This separation addresses an observed boundary in Thor's Android WebView 109.0.5414.123: after a WebView has been attached, a hidden/detached window makes its page hidden even without calling `onPause`. That version enables background scheduler freezing after a five-minute grace period. In game12, bringing this app's chat to foreground resumed the same stalled Run/Pi and drained its pending messages; this supports a hidden-page scheduling cause for that observation. It does not establish that every earlier model or stop failure had the same cause. Exact-version primary sources are [visibility and attachment handling](https://chromium.googlesource.com/chromium/src/+/refs/tags/109.0.5414.123/android_webview/browser/gfx/browser_view_renderer.cc), [the page scheduler](https://chromium.googlesource.com/chromium/src/+/refs/tags/109.0.5414.123/third_party/blink/renderer/platform/scheduler/main_thread/page_scheduler_impl.cc), and [Android's default stop-in-background feature](https://chromium.googlesource.com/chromium/src/+/refs/tags/109.0.5414.123/third_party/blink/common/features.cc). The never-attached execution-document design follows that implementation's background-operation path; Android or renderer termination still interrupts work and never authorizes replay.

The chat has no `ThorNative`, model Fetch adapter, lease, arbitrary host RPC, tool endpoint or executable-JavaScript command. Its bridge accepts only fixed UI intents, with exact origin/main-frame/instance/page checks, a fresh document generation and typed field limits. Native view results and published state feed both documents; model/transport bindings are not exposed to chat. Execution-to-chat notifications use five fixed event names, bounded metadata, local draft IDs and fixed error codes. They do not carry prompt/model/tool bodies. Hidden chat delivery is suspended; the latest state and a bounded control-event set are retained. Execution never waits for chat acknowledgement. Returning to chat receives current state and preparation status without replaying old sends.

User stop enters Native revocation independently of chat rendering, then asks the execution document to cancel Pi and persist its partial context. Work holds, foreground eligibility, explicit notification stop, single-writer close handoff, and interrupted recovery remain in force. No model wall-clock deadline was added. The Native screen-read error-priority fix is included in this later source: genuine Native refusals survive authority revalidation, rejected bodies are withheld, and successful reads retain source freshness checks.

At this documentation point the controlled software checks are Runtime139, chat/JS66, bridge13, relay3 and integration TypeScript, plus the recorded JVM/build/artifact checks. Their exact final build identity and cache status belong to the independent `tests/release-0.8-evidence/software-dual-document/` snapshot. Software success does not by itself establish Android behavior.

The new opt-in long-background test supplies real loopback SSE for 380 seconds after HOME and Activity destruction. Its measured interval observes only SQLite numbers: no JavaScript evaluation, UI return, fake clock or visibility callback can keep execution alive. It requires continuing persisted markers beyond the former five-minute threshold before reopening chat, then checks the same execution document/host, complete context and Pi follow-up. Completion and follow-up in that case happen after UI return; notification stop is covered by the separate short lifecycle case. A long stream with notification stop while still hidden remains a distinct coverage boundary. All of these new Android tests, Thor long-background behavior, cloud continuation and physical game progress require their own pinned device results; no earlier single-document pass establishes them.

## Execution-state push without chat history

The separate execution document consumes pushed state only to match preparation Run IDs, observe every session's capability epoch, and stop the matching active Run. Sending it the full chat projection on every stream update repeated the serialization and WebView delivery of messages, tool history and attachment metadata that its update handler never reads.

`ExecutionStateProjection` now copies all session IDs/epochs and active Run IDs/session IDs/status/stop reasons into a separate small object. An explicitly empty or null `activeRuns` is authoritative; only a missing field falls back to legacy `runs`. The complete chat state, chat bridge, `lastState`, Host RPC results, database and authorized task/context reads are unchanged. Concurrent sessions retain their own epoch changes and every active Run retains its stop notice. This does not alter authority, target validation or replay rules.

Five pure JVM cases cover all-session/multi-Run invalidation, the fallback boundary, exclusion of history and credentials, isolated output rows and a history object whose serialization deliberately throws. The latter still projects successfully with output below256 bytes. This is a synthetic test boundary, not a measured physical-device speed ratio.
