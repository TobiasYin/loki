# 目标、非目标与使用场景

## 定位与成功标准

[需求] 在 Thor 下屏提供简洁聊天入口，利用当前上屏应用信息回答问题，并在用户选择能力后执行操作。APK 本地承载 Agent 和工具，模型推理使用用户配置的远程服务。独立 APK 指应用本身独立分发，并不意味着无需模型/搜索服务，或无需另行启用 Shizuku。

[决定] 首版成功标准是少量可靠的完整任务闭环：读取真实环境 → 按需查证 → 必要时执行 → 提供结果和依据；不是无人值守实时游戏控制器。所有设备作用操作必须能归属到发起 Session 和 Run。

## 使用场景

| 场景 | 最少能力 | 合理执行路径 | 结果边界 |
|---|---|---|---|
| 当前模拟器版本是否过旧 | 感知＋搜索 | 应用版本工具 → 搜索发行说明 | 引用版本来源和日期；不需要截图 |
| 解释上屏游戏物品/报错 | 感知 | 一次截图 → 视觉模型；必要时搜索 | 不能识别时明确不确定 |
| 帮忙更改模拟器设置 | 感知＋操作 | UI 树或截图 → 受限触摸 → 按需复核 | 操作关闭即拒绝；不默认改文件 |
| 用手柄操作菜单或短动作 | 操作；感知视任务而定 | 按键/轴工具 → 游戏接收确认 | 原生输入来源与轴语义必须真实验证 |
| 排查闪退/渲染异常 | 感知＋调试，可选搜索 | 设备信息 → 有限日志 → 配置读取 | 私有文件不可读时提供可行替代路径 |
| 修改配置并撤回 | 调试 | 读取 → 备份 → 对比 → 写入 → 校验 → 恢复 | 不替用户臆造配置键/路径 |
| 纯问答 | 无设备能力，仍需模型网络 | 文本问答 | 不因提问自动收集屏幕 |

## 首版范围

四个固定用户能力组；内置工具注册、条件性可用状态；两个模型协议；一个已验证的搜索后端；本地会话和设置；可展开的执行记录。支持触摸和真实原生手柄是目标要求，手柄未通过 PoC 前不得声称完整满足屏幕操作能力。

## 非目标

其他安卓手机/掌机、Google Play 上架、强制 Root、系统 ROM 修改、常驻视频理解、毫秒级游戏闭环、云端 Session 同步、多人协作、任意网页获得设备桥、首版插件市场、任意第三方代码热加载、MCP 全功能客户端、OAuth 登录、内置付费模型额度、自动下载安装模拟器或游戏。

首版不保证后台长期运行、任意模拟器配置格式兼容、任意 Responses 兼容网关可用。用户自行配置端点不等于端点已通过验证。

## 两类权限的区别

系统授权是使用平台资源的必要条件；Session 开关是此会话的产品授权。二者必须同时满足。Shizuku 已授权不自动开放调试工具；无障碍已开启不自动允许截图或触摸；触摸开启不自动允许任意 Shell。

默认感知 ON、搜索 ON 只是新会话意愿值。未授予系统权限或未配置搜索凭据时展示“开启但不可用”，不静默改变默认值，也不向模型注入不可调用工具。

## 测试辅助应用范围

[需求补充] 独立上屏 Thor Input Lab APK 是手动 API 和 Agent 输入测试的共同接收端，负责原始事件、测试场景与结果，不是正式产品运行依赖。规划见 [专项设计](input-lab.md)。它不扩展产品到其他机型，不新增第五个能力开关，也不替代真实模拟器的兼容性验收。
