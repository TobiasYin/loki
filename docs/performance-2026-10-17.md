# Thor Agent 最近会话耗时分析（2026-10-17）

本次只读分析真机快照中的最近 7 条用户 Run，排除此前合成验收及本次语音开发测试。快照共 200 条 Run，均为终态。报告不包含原始提示词、回答、凭据、会话 ID、请求/响应正文；任务名称均为泛化分类。数据库和详细数值摘要仅保存在忽略的本地 build 目录。

**结论：当前主要耗时在多轮模型请求的等待和生成区间；本地准备和绝大多数设备工具本身较快。** 6 条完成任务共 167.292 秒、19 次模型请求、20 次工具调用：上下文事件到工具意图/最终结束的观测区间共 142.330 秒（85.08%），工具开始到结果共 17.945 秒（10.73%），其余本地编排共 7.017 秒（4.19%）。前一项同时包含网络排队、建连、上传、服务端计算、流式解析和少量桥接/持久化，**不能解释为服务端独占的推理时间**。

## 已确认的现象

- 6 条完成任务均使用 deepseek-v4.1-flash / low。Native prepare 为 13–16 ms；首次 authority RPC 入口为 17–23 ms；首轮上下文已准备/持久化的时间为发送后 396–466 ms。这里不支持“本地 Agent 初始化占十几秒”的判断。
- 首个 HTTP 响应头为发送后 2.211–7.446 秒。后续每轮只有 context/事件时序，没有分请求网络计时，不能把整个等待进一步准确拆成服务器排队、TLS、上传和生成。
- 调整亮度的两条任务耗时 19.345 秒与 16.306 秒，工具合计仅 1.282 秒与 0.511 秒，分别有 3 次与 2 次模型请求。屏幕点击复核耗时 30.074 秒，3 个工具共 1.160 秒，4 次模型请求。减少无效模型往返比压缩几毫秒设备操作更有价值。
- 设备侧截图 333–474 ms，点击 306 ms，亮度读取/调整 239–299 ms；Skill 读取 233 ms。联网工具属于另一类：单次搜索 1.524–1.897 秒、网页读取 2.319–3.635 秒。所有 20 次工具调用本次均没有 error。
- 每轮有效工具为 42 个；即便新会话无附件，首轮保守上下文估计已约 34,180–34,233。两条亮度追问继承上下文后约 44,729 / 53,096；联网任务最后一轮增至 73,485。估计器是一 UTF-16 code unit 加图片 reserve 的保守算法，不能等同供应商实际 token。当前未记录真实请求体大小和供应商 token usage，因此只能确认重复携带的规模，不能给出上传耗时归因。
- 屏幕点击任务发送后 4.488 秒已有思考事件，29.487 秒才出现回答文字；其间真实执行了截图、点击、复核。这是执行阶段与最终回答的差异，现有 firstVisibleTextMs 会把正在工作的任务看成“迟迟未启动”。

## 最新失败的定性

索引 0 使用 gpt-6-luna / low，2.451 秒结束为 failed。HTTP 200、92,157 字节、正常 EOF，Runtime 持久化 MODEL_OUTPUT_LIMIT / stopReason=length / LIMIT_EXCEEDED，未收到任何思考、回答或工具事件。它是输出上限结束分类，**不是网络不可达**。没有保留原始 provider SSE，不能进一步判定该响应的上游细节或把原因武断归给某个固定 token 配置。应验证该模型的输出预算与 thinking 映射，并将“达到本轮输出上限，可在同一会话继续”准确呈现；不要据此重新配置网络或丢弃上下文。分类代码位于 runtime/src/runtime.ts:421–428。

## 本轮已实施

HTTP 工作线程已从 **2 个改为 8 个**，与原有的最多 8 条 active 流准入限制对齐；最大并发流数仍为 8。这样第 3 至第 8 条已接受请求有各自的工作线程，不再因前两条响应流尚未结束或等待消费者读取而排在它们后面。保留逐请求网络策略、授权、取消、背压与结果预算，未放宽准入上限。

本轮 bridge 单元测试 **42/42 通过**，其中 Transport **21/21 通过**。并发用例在 8 条响应体均保持打开、未发放读取额度时，确认全部已接受请求都能收到响应头，第 9 条仍被拒绝；另验证取消一条阻塞流后新请求可完成，其他流保持打开，关闭后均只收到一次终态。

这是并发请求排队问题的修复，**不承诺单个任务更快**；最近会话基线也未证明实际发生了三路以上并发排队。连接池复用、逐请求分阶段计时、上下文投影与减少模型往返等建议尚未实施，下面保留只读基线与优化建议。

## 优化优先级与代码位置（读取时基线）

1. **先补分请求数值计时。** 当前 ProductHost.kt:148–173 的 ModelHttpReceipt 仅记录 status、字节和 EOF，runMetrics 只保存第一次响应头/字节；runtime.ts:80–94 的 waits 只反映当前在等待什么，没有累计值。建议每个请求记录入队、worker 开始、请求体字节、DNS/TCP/TLS、请求发完、响应头、首个 provider 活动、流结束和供应商 usage；仅保留数值/固定标签。还应记录每工具 deviceWorker 入队/开始/完成，以及 authority、context compile、persist 的累计耗时。这样才可验证下面各项收益。

2. **消除多请求之间反复建连，并修正并发容量。** native-bridge/core/src/main/kotlin/dev/thor/bridge/HttpTransport.kt:10 只有 2 个阻塞 HTTP worker，但 :55 允许最多 8 条 active 流；持续流占据 worker 到 EOF/取消，第三条开始可能等前两条释放。:60–62 每次建立独立 OkHttpClient，:34 每次完成 evictAll 并关闭其 executor，因此当前多轮请求不会复用连接池。按既有 NetworkPolicy 和凭据隔离复用连接池/Dispatcher、逐请求仍重新验证 URL/headers/authority；把模型异步调用或 worker 容量与 8 个 Run 的上限对齐。最近样本不能证明发生了三路并发排队，也不能量化复用连接会省几秒。应做受控本地 HTTPS 连接计数和三路流并发测试，然后同网同模型 A/B。

3. **减少重复模型往返，保留完整历史。** runtime/src/runtime.ts:371 明确逐步执行；当前模型经常单独截图→模型→点击→模型→截图→模型。可提供一次观测同时返回 app/window/紧凑树的复合读取，并在动作结果中附上受限的新观测引用，省掉仅为查状态再发一轮模型。不能批量猜测 UI 输入、自动重放旧动作，必须继续保留新页面的目标/授权检查。亮度已知上下屏目标可在同一模型响应生成两屏调用；不应对简单百分比调整反复探索全量配置。

4. **优化给模型的投影，不能清空 Pi session。** runtime/src/runtime.ts:368–407 已复用同一会话的 Pi Agent；真正请求仍由 compileContext 的有界 Native 历史决定。:384–390 每轮重新解析当前 Run 所有附件，runtime/src/context.ts:142–158 先解析最多 50 个历史 turn 的附件，再删超预算 turn，并对带 Base64 的完整投影做 SHA256。当前长 Run 的旧截图一直随上下文发送至过期/预算排除。可按任务/权限/过期/配置版本缓存不可变的文本投影，先根据附件元数据预估预算，再加载入选图片；旧截图在模型投影中变成带来源的文字事实，保留最新必要视图。完整持久化证据、用户约束、副作用账本、工具调用/结果配对和失败后的同会话续接均应保留。能力撤销和图片失效仍逐请求检查。

5. **工具目录分阶段，静态事实去重。** runtime/src/context.ts:123–133 给模型带全量 schema 和至多 4 KiB Skill 元数据；本次有效目录固定 42 项。可研究按当前任务启用的一小组工具和 discover 工具降低 schema 负担，但新增能力必须对模型可发现，不能隐藏用户已经授权的能力。runtime/src/runtime.ts:176/184/186/198/209 每次工具约 5 次 authority 读取；ProductHost.kt:414–490 每次重建 backend availability 和上屏上下文。可以缓存纯静态 backend 事实，不能删除实际提交前或异步结果后的授权/窗口校验。Presentation 证据准备在 ThorAccessibilityService.kt:94–116 最多等 1.5 秒，本次没有分阶段时序，尚不能断言它是瓶颈。

6. **启动和 UI 属于次要、可独立优化的部分。** SqliteStore.load（Storage.kt:34–41）启动时加载所有事件与 Base64 附件；旧独立证据曾实测 store.load=2.260 秒、engine→ready=2.874 秒（tests/release-0.8-evidence/game/progress.json 的 startupObservation），不代表本次热发送耗时。可分页加载历史和按需读取附件。现有 StreamEvents 已 40 ms 聚合、首片立即；Native publish 50 ms、LatestValue 50 ms；ChatEventProjection/EventIndex 已增量，executionWeb 已使用最小状态投影。剩余 chatSnapshot 全选中会话序列化，以及 ui.js:358–368 的 run 签名/当前展开结构重建可用增量事件更新减少 CPU，但本次没有 UI 帧时间，不能宣称它解释十几秒等待。

## 验证边界

- 会话耗时分析来自改动前的只读快照，没有改模型配置、历史、权限或设备状态；本轮另外完成了上文列出的 HTTP 工作线程修复与软件测试。语音上下文功能由独立工作实现，本报告不替代其验收。
- 85.08% 是按事件划分的请求等待/生成观测区间，不是供应商推理 CPU 的占比；10.73% 工具区间也包括 web 工具的网络等待。
- HTTP 并发排队修复已通过上述受控测试；连接池复用等其余建议尚未实施，所有建议均没有单任务前后对照加速数据。本次不宣称已提升百分之多少，也不以旧失败或旧 cold-start 代表当前版本的所有行为。
